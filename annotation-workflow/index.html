Inline annotations → Claude Code

A pattern for reviewing AI-generated docs without copy-pasting whole paragraphs back to the model.

~5 min read · select any text below to leave a comment · download this page

The whole idea in one paragraph

When Claude writes a long doc or design, the natural review step is reading it and noting what's wrong, in-place. Saying that back over chat ("in the third paragraph of section 2…") is slow and lossy. Instead: open the doc as an HTML page with an inline-annotation overlay; highlight any phrase, leave a comment; the comments stay in your browser; when you're done, click Copy and paste the JSON back into Claude Code. Claude then knows exactly which phrase each note refers to and can address every annotation in one pass.

1 The problem

A typical Claude Code workflow produces long, well-structured Markdown (design docs, project plans, API specs). Reading them critically and giving structured feedback is harder than it looks:

  • Pointing at a specific sentence over chat means either pasting the surrounding paragraph or describing the location ("in §3, the second bullet…"). Both are friction.
  • Multiple small notes scattered across the document don't batch well — by the time you've quoted all the context, you've typed more than Claude.
  • Without anchors, Claude can mis-target an edit and rewrite the wrong sentence.

The annotation HTML pattern fixes all three.

2 What the annotation HTML is

A single self-contained HTML file that renders the same content as the underlying Markdown, plus three pieces of UI: a "+ Comment" pill that appears on text selection, a popover for writing the comment, and a side panel that lists every comment. Comments are anchored to the exact phrase that was selected — the quote — and stored in the visitor's browser only (localStorage). Nothing leaves the browser unless the visitor clicks Export, Copy, or Download.

The HTML is the artifact you share. Drop the file into a GitHub Pages folder, scp it to a colleague, or just open it locally — every reader gets the same annotation UI, with their own comment list. Their comments never reach you (or anyone else) until they actively send the JSON back.

3 The annotator's workflow

From the reader's perspective:

① open

Load the page

HTTP, local file, GH Pages, IDE proxy — anything that serves the HTML.

② select

Highlight a phrase

Any chunk of text in the doc. A purple "+ Comment" pill appears below the selection.

③ comment

Type the note

Specific suggestions ("rename this to X"), open questions, or just "this is wrong, see file.py:42".

④ copy

Click 📋 Copy

All comments are formatted as JSON and put on the clipboard. Paste straight into Claude Code.

Optional buttons in the side panel: Export downloads the same JSON as a file; Import loads someone else's JSON; Hide resolved shrinks the noise once items are addressed; Clear all resets.

4 The JSON format

Every comment is one object. The full payload is:

{
  "annotations": [
    {
      "id":      "amp15zxyfz4n",                       // stable per-comment, generated client-side
      "blockId": "b12",                                // which paragraph/heading was hit (internal anchor)
      "quote":   "the exact text that was highlighted",
      "comment": "what the reader wants changed or asked",
      "status":  "open",                                // or "resolved" once handled
      "ts":      1715000000000                          // epoch ms — useful for sorting
    }
  ]
}

Two fields do all the load-bearing work:

  • quote — the exact substring of the source. Claude uses this to locate the right place in the file (a plain grep or string search; the quote is guaranteed to be a verbatim slice of the doc when it was annotated).
  • comment — the natural-language instruction. Free-form. May be a question, a correction, or a directive.

Caveat — drift. The quote is verbatim against the doc as the annotator saw it. If the doc has been edited since (e.g., Claude already rewrote it), the quote may not match anymore. In that case, fall back to the surrounding context in the comment, or ask the user to re-annotate the new version.

5 How Claude Code should handle a paste

When a chat message contains the annotations JSON (recognisable by the top-level {"annotations": [...]}), follow this procedure:

① identify target

Which file?

Check the surrounding conversation for the source file path. If unclear, ask once.

② locate each quote

grep the source

For each comment, search for the quote string in the target file. If it doesn't match exactly, search for the longest unique prefix.

③ interpret intent

What does it want?

The comment is natural language. Decide whether it's an edit, a question, or a meta-note (e.g., "this whole section is unclear").

④ act + report

Address & summarise

Apply the edit (or ask for clarification). End with a tight summary: "addressed N of M comments; flagged K as ambiguous."

Order of work matters less than order of reply: walk through the comments in document order, not JSON order, so the user can trace your response against the doc visually.

Don't silently rewrite outside the quoted span. Annotations are scoped suggestions. If the comment hints at a larger refactor, propose the wider change before doing it.

6 Examples

Example 1 — a direct edit

JSON received
"we will use Python 3.10"
make it 3.11, we standardised on that across the repo
Claude's action
grep "we will use Python 3.10" in the README; replace with "3.11". Report: "Done — README.md line 24."

Example 2 — a question, not an edit

JSON received
"map-derived poses are handed to the optimizer directly"
how robust is this if the generator wildly disagrees with the map?
Claude's action
No code change. Reply inline: explain the SDS regularizer falls back to refining poses; propose adding a clarifying paragraph if useful.

Example 3 — meta / structural

JSON received
"§4 The main risk"
this section is too short; expand on consistency mitigation #4
Claude's action
Locate §4 by heading text; rewrite the mitigation list to expand item 4 (diffusion regularizer) into 2–3 sentences with concrete loss-formulation hint.

7 Producing an annotation HTML for any doc

The HTMLs are templates: the chrome (TOC, annotation layer, sidebar, download) is constant; only the body content changes. To wrap a new Markdown doc:

  1. Copy an existing annotation-HTML page (e.g. 3dgs-explainer or this one).
  2. Replace the content inside <div class="paper" id="paper">…</div> with the new doc, formatted as semantic HTML (h2/h3/p/ul/code…).
  3. Update <title>, the .draft-tag, and the breadcrumb links.
  4. If the doc references images, link to them relatively; for offline portability, base64-inline them in the Download HTML function (already implemented in the explainer template).

The annotation JS handles itself: it auto-tags every p/li/h2/h3/pre with a data-aid so quotes can be resolved later.

8 Future: a Claude Code skill

Once the workflow is settled, the recognition step ("this paste is an annotations JSON, here's what to do") becomes a skill — a SKILL.md file in ~/.claude/skills/ or a project's .claude/skills/ that triggers on the JSON shape. The skill's body would be a tightened version of §5 above: identify the target file, grep each quote, interpret intent, address + report. Once the skill exists, Claude Code recognises annotation pastes automatically and follows the procedure without being prompted.

This page is the design doc for that skill. Highlight anything that's wrong, ambiguous, or missing; the comments will become the spec. Once the spec settles, the skill itself is a near-mechanical translation.
